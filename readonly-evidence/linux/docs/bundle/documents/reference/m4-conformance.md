# Public M4 conformance and publication boundary

The fixed registry defines twelve primary rows: six execution modes on Linux x86-64
and Windows x64, with each row retaining its exact runner baseline. Unresolved runner aliases
require an authenticated actual observation before a concrete OS claim. [The support contract](M4_SUPPORT.md), the compiled CLI JSON and
authenticated Markdown export must project the same complete registry digest and matrix.
These files report static requirements. They certify no execution, current installation,
successful CI run, signature, deployment or milestone closure.

## Required evidence

Closure follows #400, reviewed and integrated #401, then #402. Failed runtime behavior returns
to its owning issue. Keep the complete M0–M3 contracts, registries and required host gates.
Every advertised row needs independent evidence at the actual candidate commit/tree:

- Each mode's independently pinned contract plan defines its required case kinds. Exact-limit
  and first-extra pairs must execute at their owning boundary wherever the reviewed contract
  requires them. Fixed policies and precise typed public-input exclusions retain their owning
  enforcement and binding proofs. A mapped test is not a pass; zero, ignored-only, skipped, filtered-out, timeout,
  truncated, missing or expired results cannot qualify a required case.
- Bind exact source, WIT closure, component/core/interface/binding, toolchain, manifest and
  bundle inventory identities. Specified-only WIT eligibility never supplies an effective grant.
- Independently replay deterministic artifact bytes on each required host. Retain both actual
  execution manifests, comparing their invariant fields without pretending dynamic endpoints,
  counters and outcomes are reproducible artifact bytes.
- Record actual capability-denial and hostile component/binding probes at their owning boundary.
  Distinguish one private literal environment key, empty status grants, and separately approved
  one-read clock grants. Listener approval never grants guest clock permission.
- Account for finite deadlines, attempts, serial concurrency and actual owned Store/resource/
  worker/listener cleanup. Forced process termination establishes handle release only and cannot
  certify graceful teardown or uncommitted result publication.
- Require complete local M0–M4 gates and authenticated exact-source Linux/Windows hosted
  checks, including pinned real-browser and fresh installed-command evidence. A different
  commit's equal tree, ancestry or check name cannot silently substitute for this revision.

Default components are build-only and have no guest lifecycle. Browser elapsed-time checks
are post-hoc and cannot preempt synchronous guest execution. Preserve these explicit lifecycle
exemptions. Windows Server 2022 receipts do not establish desktop Windows portability.

The registry references an independently pinned source-contract plan. Every advertised limit
retains its contract identity, source bindings, semantics and emission, loader or runtime domain.
Mappings distinguish `mapped`, `partial`, `unresolved` and formally `excluded` boundaries.
The support JSON preserves partial and unresolved requirements as explicit `proofGaps`; it
also preserves all typed exclusions and their source proofs. Owning guard tests, public
bindings and public admission tests serve distinct requirements. A private guard prerequisite
cannot replace a required reachable public component-byte pair.

A quantitative canonical-public-shape exclusion retains its reviewed expression, literal,
export and framing bounds and the named actual baseline measurement case. Authenticated
evidence must collect the actual component-byte metrics and apply that bound below the
advertised ceiling; a static bound does not certify runtime acceptance at the ceiling.
The coverage checker identifies missing mappings but cannot certify execution. Every row
remains `not-evaluated` in `zryna support --json`, including complete mappings and exclusions.
Resolve gaps with owning tests or reviewed precise exclusions; documentation claims cannot
replace failed or absent gates.

## Documentation and live publication

Keep `zryna.docs.bundle.v1` unchanged. The canonical support JSON fence belongs to the
whitelisted `M4_SUPPORT.md` document; its bytes are covered by the normal bundle manifest.
Do not add an unmanifested JSON sidecar. Authenticate the successful final-main source,
workflow run/attempt, artifact/archive and independently obtained manifest digest before import.
Dedicated workflow publication must authenticate complete exact-main foundation/M4 success;
cross-workflow success cannot be expressed by an unrelated YAML `needs` alone.

The website imports the reviewed next-channel Markdown bundle through its existing locked
importer. Preserve immutable release bundles and generated release pages. Require canonical
matrix equality in built and served support pages, with missing/extra/altered rows, exclusions,
limits and digest rejected. The final receipt separately binds compiler commit/tree and registry
digest, documentation run/attempt/artifact/archive/manifest, website commit/tree/import lock,
both required website jobs, observed deployment/image identity and bounded live response hashes.
A source file, local export, CI upload or static health endpoint cannot establish live publication.
A PR receipt does not transfer to a merge revision or subsequent deployment.

## Distribution restrictions

Only a newly complete content-verified installation has the bounded installed H1 row.
Existing immutable beta archives retain their historical exclusions. Installed components,
browser and server modes remain unavailable. Content verification is separate from signed
public-release authentication: preserve the existing cosign certificate identity and OIDC issuer
checks if signed artifacts are ever advertised. This task adds no signed release, tag authority,
general WASI grant, general cloud hosting or production admission.
